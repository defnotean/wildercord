# Bounded paired Crimson Moon capture

This adapter selects one existing-art action: `articulated_netherite_funded_right_release`. It uses the shared two-client launcher, a real owner and a distinct connected TCP observer. The cast-receipt route retains the original 42 cases and appends the four separately reviewed Life comparisons, for 46 mandatory cases. The existing `connected-combat-native` job runs that complete roster first, then four sequential Moon views. The Moon route does not join the ordinary one-client descriptor or add a job.

## Fixed coverage and resources

Four separate runs cover original wide and slim skins at `front_oblique` and `reverse_oblique`. Profiles are fixed to `moon-wide` (`WCMoonWide2`) or `moon-slim` (`WCMoonSlim`); the peer is `WCAuraPeer`. Each fresh run admits one actual full/full/full/low Final and captures owner first person plus observer world view of that same accepted action. The right hand, netherite armor and funded shell are fixed for this bounded slice.

Each run has two owned client JVMs, at most 2 GiB heap per JVM and a 180-second default and maximum deadline. Cast receipts retain their 900-second supervisor ceiling. The job retains its 30-minute limit and 24-minute native/export step. `tools/native/run_paired_matrix.py` imposes a 1,380-second actual elapsed budget across both Gradle exports, validation and all five groups. Later group ceilings are clipped to the actual remaining time; the sum of individual maximum ceilings is not an admission test. One checkout lock is retained across exports and clients, so groups cannot overlap. A one-shot alarm interrupts work on expiry; bounded owned-process cleanup and evidence persistence finish before the elapsed budget is rechecked. The outer minute reserves room for that cleanup. Any failure stops later groups and leaves their required entries `not_started` in `matrix-result.json`.

Output must be fresh. The existing accepted-EULA-file route and explicitly authorized disposable CI route remain unchanged. No arbitrary case, username, JVM argument or executable can be supplied. Exports run without client JVMs and their owned process groups are terminated/reaped before launch. The 600-tick rest is preserved; the fixture neither resets rest nor repeats the action in the fresh world.

After source review, an exported launch can be selected with:

```sh
./gradlew -I tools/native/export_two_client_launch.init.gradle exportTwoClientLaunch -PtwoClientSuite=moon -PtwoClientLaunch=build/native/moon-launch.json
python tools/native/launch_two_clients.py build/native/moon-launch.json --output build/native/moon-wide-front --suite moon --profile moon-wide --case articulated_netherite_funded_right_release --observer-angle front_oblique --accepted-eula path/to/already-accepted-eula.txt
```

The example explicitly selects the same export path for both commands. These commands are documentation, not a native execution receipt. Direct `runClientGameTest -PtwoClientSuite=moon` fails because the second actual client must be supervised.

The fixed CI matrix is selected with `python tools/native/run_paired_matrix.py --output build/native/paired-matrix --total-timeout 1380`, inside the existing virtual display. The exact ordered cast contract is read through the shared supervisor; no separate shortened roster exists in the matrix runner. Each Moon view gets a fresh launch nonce and game directory. The matrix rechecks the exact head, PR head, run/attempt, selected skin/angle, two process exits, terminal ledger and complete image proofs before recording success. The launch export and a byte-identical descriptor snapshot remain alongside each group’s original logs, receipts and screenshots.

## What the receipts establish

The launcher binds exact checkout SHA, optional separate PR-head SHA, descriptor and runtime hashes, fresh nonce, run identity, both fixed UUIDs, actual process IDs, selected case, original skin and observer angle. The processed contract and passive mixin descriptor must match reviewed source. Paired hooks replace the owner-only hook configuration so the same injection cannot run twice.

Java receipt validation compares actual deferred geometry and item matrices with independently sampled source body and view palettes. It binds the full extracted action/frame identity, eligible hand/model/equipment/funded shell, original skin and submitted material. For observer geometry it retains the independently verified enclosing PlayerModel root, including visibility, rechecks it during deferred body preparation and world-item entry, and uses that retained root for the expected item matrix. The supervisor requires exactly one of each role-specific pass, complete nested Classic and articulated frame identities, the same positive remote item identity across all world passes, and explicit segmented backend, original material and eligible-hand witnesses. Every terminal must retain the complete accepted action. The callback pixel hash must equal the decoded unchanged PNG. The launcher rechecks numeric comparisons, identities, hashes and image bytes before accepting terminal witnesses.

Server completion must occur exactly ten ticks after acceptance. Each image must come from the renderer's strict `ACTIVE [10,11)` source window after reading the immutable server release receipt. The local sequence must strictly order release read, source frame, extraction, render and GPU copy. At the first actual direct-damage callback, both complete image witnesses must already exist. Their hashes must remain unchanged through final validation. The final case and both process terminals retain acceptance-relative damage age 11–15 and release-relative delay 1–5.

This establishes a causal interval: server release, image extraction and persisted image witnesses, then first actual direct damage. It does not establish equality between a remote client's rendered frame and the server release frame. `serverReleaseFrameCorrespondenceVerified` therefore remains false on every witness and result. Only the final case and terminals may set `releaseImageDamageOrderVerified=true`; an image alone leaves that field false. No filesystem timestamp or cross-process clock inference is used.

## Original-frame review packages

The full `connected-combat-native` artifact is uploaded with `always()`, including partial failures. The separate `tools/curate_moon_frames.py` package stays strictly below 14,000,000 bytes, including its manifest and receipt JSON. It copies original PNG and JSON bytes without resizing or re-encoding, checks every PNG chunk CRC and binds decoded pixels to callback hashes. Remote views receive priority, then owner FP; any originals that exceed the budget stay in the full artifact with omission reasons, paths and hashes in the index.

Every candidate binds exact checkout/PR head, workflow run/attempt, launch nonce, original skin, observer angle, selected action and original file hashes. A log-selected receipt can inherit a causal group claim only if its exact receipt path/hash, PNG path/hash, callback hash and name match that role’s revalidated observed witness. Failed groups and rejected records retain a `diagnostic-` filename and false causal/visual claims. Missing or stale evidence is listed explicitly. A small package is not human visual acceptance, and a successful subgroup does not make a failed matrix pass.

The same collector’s `--owner` mode fixes the separate owner FP diagnostic upload. It reads the exact current log marker’s receipt path, including non-first sequence numbers such as `000009.json`, rather than globbing every prior UUID or assuming `000001.json`. It accepts at most one selected release case/original skin, requires current owner-launch nonce and run/head identity, enforces the game-directory receipt whitelist, and preserves original image/receipt hashes. A missing receipt is never marked verified. Owner diagnostics keep remote-observer, causal ordering, exact server-frame and human visual acceptance claims false.

## Verification limits

The Python controls use synthetic receipt files and fake process handles. They check exact matrix order, elapsed-budget clipping, interruption during cleanup, missing-case/provenance rejection, distinct nonces, path and symlink rejection, CRC/hash mutation, current-log receipt association, bounded original packaging and diagnostic labeling. They are not actual multiplayer or GPU captures. Java compilation and numeric mutation controls are source evidence. Native execution and human review of silhouette, blade visibility, materials and armor/shell quality remain required. `pixelQualityReviewed` stays false in machine output.

This one release slice does not establish the 60-case owner phase/hand/fallback matrix, cancellation appearance, delayed-damage appearance, or exact server-frame correspondence. Current native acceptance for this paired Moon adapter remains pending. The existing owner-only capture and core gameplay timeline are separate source and native gates.
