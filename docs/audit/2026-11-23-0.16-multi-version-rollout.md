# 0.16.0-alpha multi-version rollout (started 2026-11-23)

`main` (Minecraft 26.3) carries the 0.16.0-alpha feature wave: **130 commits, 124 of them
code, ~720 source files, 60k insertions** over the point every down-port branch was cut
(`47b0ade12`). This campaign brings that wave down the whole ladder and then lists several
Minecraft versions on CurseForge and Modrinth, where today only `+mc26.3` exists.

## Decisions (owner, 2026-11-23)

- Port **all 14** down-port branches.
- Publish **1.21.4 and up** to CurseForge and Modrinth. The 1.21.3/1.21.2/1.21.1 rungs drop
  custom entity renderers, so the new knights, ocean creatures and White Rabbit would be
  invisible there; they stay on GitHub only.
- Version number **0.16.0-alpha everywhere**, so the stores show one release across
  `+mc1.21.4` … `+mc26.3`.
- **Publish only** - the live server keeps the `54ee54bd` jar (no staging).

## Per-version loop

Each rung repeats the established port verification, against the branch above it:

1. `git merge` the parent version's branch; resolve conflicts on port-helper surfaces only
   (compat seams, gametest compat/mixins, datapack/resources, build descriptors).
2. Four VPS compiles (`compileJava`, `compileClientJava`, `compileTestJava`,
   `compileGametestJava`) EXIT 0 and `verify_port.py` `VERIFY EXIT 0`.
3. `port_helper.py diff-surface --base <parent> --allow-identifier-migration` EXIT 0.
4. `run_vps_checks.py build --head <sha>` gate, receipt recorded.
5. `build_profiles.py` + `audit_packages.py`.
6. Ledger round here and in `docs/audit/2026-10-24-polish.md`.
7. Push.

Ladder order: `main(26.3)` -> `26.2` -> `26.1.2` -> `26.1` -> `1.21.11` -> `1.21.10` ->
`1.21.9` -> `1.21.8` -> `1.21.7` -> `1.21.6` -> `1.21.5` -> `1.21.4` -> `1.21.3` ->
`1.21.2` -> `1.21.1`.

## Publishing notes

- `tools/curseforge_upload.py` hard-codes `gameVersions = [17045, 7499, 14454, 9638, 9639]`
  for the 26.3 jar. Each down-port needs its own CurseForge game-version IDs pulled from the
  game-versions API before upload.
- `tools/modrinth_upload.py` derives `game_versions` from the jar's `+mc<X>` suffix, so it
  needs no per-version table.
- Tokens (`CURSEFORGE_TOKEN`, `MODRINTH_TOKEN`) are User-scope environment variables on the
  Main PC; uploads run from there, not the VPS.
- `docs/releases/0.16.0-alpha.md` is the changelog both stores read; it must exist on every
  branch that publishes.
